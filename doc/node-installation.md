# Установка ноды через SSH

В меню «Ноды и расширения → Добавить ноду» работает поэтапная установка на отдельный VPS. Панель должна быть установлена этой Go-версией и иметь действующий API-токен. Мастер создаёт профиль VLESS Reality с Vision, inbound на TCP 443, ноду с API на 2222, хост подписки и internal squad. Доступ пользователям выдаётся назначением этого squad в панели; мастер не меняет существующие назначения.

## Требования

- Чистый выделенный сервер: Debian 12/13 или Ubuntu 22.04/24.04, amd64/arm64, systemd и root SSH.
- Публичный адрес ноды и отдельный DNS-домен selfsteal, направленный на эту ноду. Домены панели и подписки использовать нельзя. IDN вводятся в punycode.
- Email администратора в настройках RemnaManager для ACME, исходящий HTTPS и доступность TCP 80 для проверки домена.
- IP панели определяется автоматически по SSH-соединению со стороны ноды, с учётом NAT. Мастер предложит проверить адрес перед началом установки. При нескольких интерфейсах или разных маршрутах SSH и backend его можно исправить: нужен IP, с которого панель действительно подключается к API ноды.
- OpenSSH на управляющем сервере. Поддерживаются стандартные ключи, SSH agent, необязательный абсолютный путь к ключу или пароль, который запрашивает сам OpenSSH.

Мастер отказывается от установки поверх существующей панели, конфигураций прокси и занятых портов 80/443/8443/2222. Активные UFW/firewalld и чужие фильтрующие правила INPUT требуют предварительной миграции. SSH-порт не должен совпадать с портами сервисов.

## Порядок работы

1. Укажите имя, публичный IP/домен ноды, SSH-порт и домен selfsteal. IP панели оставьте пустым для автоопределения; при необходимости можно задать его вручную. Путь к SSH-ключу также необязателен.
2. Сверьте полный SHA256-отпечаток Ed25519 host key через консоль хостинга и введите его. Изменившийся ключ требует повторной проверки.
3. Проверьте итоговые параметры и подтвердите установку. OpenSSH запросит аутентификацию. Если IP панели не был указан, мастер прочитает адрес клиента из `SSH_CONNECTION` на ноде и предложит проверить или исправить его. Если определить адрес не получилось, доступен ручной ввод. До подтверждения адреса пакеты и firewall ноды не меняются. Затем мастер выполнит проверку VPS, установку зависимостей, получение ключа панели и закрепление официального образа ноды по digest.
4. Мастер установит Nginx, сертификат и сайт прикрытия, запустит ноду, создаст объекты панели и дождётся подключения.
5. После применения полного firewall откройте **новую SSH-сессию к ноде**. Только после успешного входа нажмите Enter в мастере для сохранения правил. Без подтверждения независимый таймер systemd вернёт прежние правила через 120 секунд.

Nginx обслуживает ACME на TCP 80 и HTTPS сайта прикрытия только на `127.0.0.1:8443`. Внешний TCP 443 занимает Xray Reality; его target направлен на локальный Nginx. Сертификат продлевает certbot с проверкой конфигурации и перезагрузкой Nginx. Для ноды используется Nginx; выбор Nginx/Caddy остаётся в установщике панели.

## Firewall

Перед запуском контейнера API на TCP 2222 уже ограничен указанным IP панели. Полная политика применяется отдельным этапом:

| Назначение | Доступ |
| --- | --- |
| SSH | Порты из эффективной конфигурации sshd и текущей SSH-сессии |
| TCP 80 | ACME и перенаправление HTTPS |
| TCP 443 | Клиентские подключения Reality |
| TCP 2222 | Только IP панели; loopback разрешён |
| TCP 8443 | Только loopback |
| Остальные новые входящие подключения | Закрыты |

Правила действуют для IPv4 и IPv6 в собственной таблице nftables `inet remnamanager_node`. Сохраняются established/related, loopback, ICMP и DHCP. Входящий транзит закрыт, включая публикации Docker; исходящие подключения Docker разрешены. Глобальный ruleset не очищается, firewall хостинга не меняется.

Пробные правила не заменяют сохранённую политику до явного подтверждения SSH. При перезагрузке во время проверки загружается прежняя сохранённая политика. Таймер отката не зависит от окна TUI или управляющего SSH-процесса. После истечения срока нужно возобновить установку и повторить проверку.

## Продолжение и секреты

Esc останавливает дальнейшие шаги, сохраняя уже выполненные действия. Установленные пакеты и созданные объекты панели автоматически не удаляются. Если firewall находится на проверке, таймер остаётся включённым.

«Незавершённые установки» загружает журнал, повторно проверяет host key и подключение, затем повторяет проверки и незавершённые действия. Ключи Reality, short ID, ключ ноды и закреплённый образ сохраняются. Повторный запуск находит прежние API-объекты даже после потери ответа на создание. Изменённые вручную профили и удалённые сохранённые объекты вызывают ошибку вместо автоматической замены.

- Управляющий сервер: `/var/lib/remnamanager/node-jobs/ID.json`, права 0600, каталог 0700. Журнал содержит секреты и включается в резервную копию панели. Не удаляйте его для повторной попытки.
- Сервер ноды: `/opt/remnanode/compose.json` и `/var/lib/remnamanager-node/install.log`, закрытые для других пользователей. Каталог агента содержит идентификатор владельца, состояние firewall и файлы отката.
- Пароль SSH не читается приложением и не записывается. Ключи и Compose передаются через stdin SSH, без секретов в аргументах процесса. Host key закреплён в отдельном known_hosts; пользовательский SSH config и перенаправление agent отключены.
- Между этапами используется временная SSH control-сессия. Она закрывается при завершении приложения, а при аварийном выходе истекает после 120 секунд простоя.

Установку нельзя переносить на другой сервер путём подмены адреса в журнале. При потере журнала восстановите его из закрытой резервной копии. [Обновление контейнера ноды](node-update.md) реализовано отдельно. Переустановка, смена selfsteal и отдельное обновление Xray пока не реализованы.

## Проверки и границы проверки

`go test ./...` проверяет валидацию, сохранение и восстановление ключей, защиту от дубликатов API, порядок этапов, явное подтверждение firewall, отмену и размеры терминала от 36×18 в ASCII/ANSI/ANSI256.

В одноразовых контейнерах проверены:

- Настоящие backend и remnawave/node: создание Reality-профиля, подключение, восстановление объектов без дубликатов, получение пользовательской подписки с ожидаемыми ключом, SNI и Vision (`TestLiveNodeProvisioningAPI`). Используется только изолированный проект `rmgo-nodes-test-*`, см. [проверки управления нодами](node-management.md).
- Настоящий OpenSSH: закрепление host key и повторное выполнение команд через control-сессию после удаления тестового клиентского ключа (`TestLivePinnedSSHConnection`).
- Настоящий nftables и сетевые запросы из отдельных контейнеров: API только с IP панели, сохранение SSH/HTTP, блокировка лишних портов и DNAT, откат собственной таблицы (`tests/node-firewall.ps1`).
- Этапы удалённого Bash-агента с настоящими Nginx, TLS и nftables: проверка занятых портов, конфигурации, просроченное подтверждение, откат, повторная проверка и сохранение правил (`TestNodeAgentStagesInDisposableContainer`). В этой проверке Docker, ACME и systemd заменены управляемыми тестовыми командами.

Для проверки Bash-агента на Linux:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go test -c -o /tmp/remna-nodes.test ./internal/installer
docker build -t remna-node-agent-test -f tests/docker/node-agent.Dockerfile tests
docker run --rm --network none --cap-add NET_ADMIN \
  -e RM_AGENT_STAGES_INTEGRATION=1 -v /tmp/remna-nodes.test:/nodes.test:ro \
  --entrypoint /nodes.test remna-node-agent-test \
  -test.run=TestNodeAgentStagesInDisposableContainer -test.v
```

Полная установка на публичный VPS с настоящими ACME, пакетным менеджером, systemd-таймером и перезагрузкой ещё не проверена сквозным тестом. Контейнерная проверка этих интеграций не заменяет.
