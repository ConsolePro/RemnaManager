# Установка панели и компонентов

В Go-версии пункт «Панель и компоненты → Установить панель» выполняет настоящую установку. Для просмотра интерфейса без изменений системы используйте `remna --demo`.

## Требования

Чистый выделенный VPS: Debian 12/13 или Ubuntu 22.04/24.04, amd64/arm64, root, работающий systemd и SSH. Нужны исходящий HTTPS, DNS и два разных домена с A/AAAA на этот сервер. Внешний firewall провайдера должен пропускать SSH и TCP 80/443; Caddy также использует UDP 443. Если опубликована AAAA, IPv6 тоже должен работать. Домены IDN вводятся в punycode.

Существующие чужие установки в `/opt/remnawave`, конфигурации Nginx/Caddy и активные входящие правила UFW/firewalld/iptables/nftables требуют отдельной миграции: установщик останавливается вместо перезаписи. Для проверки занятых портов нужна `ss` (пакет `iproute2`). Существующий Docker должен иметь Compose и Engine 28+; автоматическое обновление чужого Docker не выполняется.

## Мастер

1. Проверяет ОС, права и действующие SSH-порты.
2. Предлагает Nginx + Certbot или Caddy с автоматическим HTTPS.
3. Запрашивает домены, имя администратора и SSH-порты; email берётся из настроек.
4. Показывает параметры и ожидаемые изменения перед запуском.
5. Проверяет DNS, занятые порты и принадлежность конфигурации.
6. Устанавливает недостающие пакеты и Docker из официального репозитория.
7. Создаёт Compose-конфигурацию, запускает PostgreSQL, Valkey и Remnawave; ждёт готовности панели.
8. Создаёт администратора, отдельные токены управления и страницы подписок; запускает страницу подписок. Токен подписок имеет ограниченные права.
9. Настраивает прокси, сертификаты и автоматическое продление, проверяет публичный HTTPS с проверкой доверия сертификатам.
10. Применяет firewall с независимым таймером отката на 120 секунд. Для сохранения правил нужно открыть второе SSH-соединение и подтвердить доступ в мастере до истечения срока. Установщик не может самостоятельно доказать доступность нового SSH-соединения извне.

Девять операций после подтверждения отображаются отдельными этапами с прогрессом и ошибками. Esc отменяет дальнейшие операции; уже выполненные изменения не удаляются. Если firewall ожидает подтверждения, независимый systemd-таймер продолжает работать после выхода или разрыва SSH.

## Порты и хранение

Новые входящие соединения разрешены только на выбранные SSH TCP-порты, TCP 80/443 и UDP 443 для Caddy. Сохраняются loopback, установленные соединения, ICMP/ICMPv6 и DHCP. Остальные входящие соединения IPv4/IPv6 блокируются, включая новые внешние DNAT-соединения к Docker. Исходящий трафик и исходящие соединения стандартных Docker-мостов `docker0`/`br-*` разрешены. Маршрутизаторы, VPN-шлюзы, macvlan и нестандартные сетевые схемы требуют отдельной настройки; мастер рассчитан на выделенный сервер панели.

Панель публикуется только на `127.0.0.1:3000`, страница подписок — `127.0.0.1:3010`. PostgreSQL и Valkey не публикуют порты хоста. Правила находятся в собственной таблице `inet remnamanager_go`; таблицы Docker не очищаются. После подтверждения отдельный systemd-сервис восстанавливает правила при загрузке, не переписывая `/etc/nftables.conf`.

Compose и env: `/opt/remnawave`. Состояние, случайные секреты и приватные журналы: `/var/lib/remnamanager`. Каталоги закрыты правами 0700, файлы с секретами — 0600. Пароль администратора показывается в результате и сохраняется в `panel.json`; сохраняйте его как секрет. Журнал может содержать диагностический вывод контейнеров, поэтому также закрыт от других пользователей.

Повторно запустите тот же мастер с сохранёнными доменами, прокси и администратором для продолжения после ошибки. Секреты и данные БД сохраняются; готовность сервисов и действительность токенов проверяются снова. Смена доменов, прокси или администратора через повторную установку не поддерживается. Не удаляйте состояние отдельно от стека. Нельзя восстанавливать удалённую БД простым повторным запуском при старых токенах — мастер сообщит об ошибке.

Базовая версия backend закреплена на `3.4.9`, PostgreSQL — `18.4`. Образ страницы подписок первоначально загружается из официального `latest`, затем его digest сохраняется для повторных запусков. Удаление компонентов, установка нод и остальные разделы меню пока остаются «В разработке».

## Управление установленными компонентами

Все пункты раздела «Панель и компоненты» подключены к настоящим операциям. В `--demo` управление отключено с явным сообщением. Для работы необходимы собственный маркер стека и состояние Go-установщика; установка Bash автоматически не импортируется.

| Пункт | Поведение |
| --- | --- |
| Обновить панель | Запрос стабильной версии `X.Y.Z`, проверка официального GitHub Release, загрузка образа, остановка API, копия БД и конфигурации, запуск backend и проверка готовности. PostgreSQL/Valkey и их версии не меняются. Понижение версии запрещено. |
| Остановить панель | Останавливает панель, подписку, БД и кеш этого Compose-проекта. Не удаляет тома, сертификаты, прокси или firewall. |
| Логи панели | Последние 100 строк каждого из четырёх сервисов. Управляющие последовательности удалены; известные секреты скрыты. Это снимок, повторный выбор обновляет вывод. |
| Статус компонентов | Реальный `docker compose ps --all`, версии, адреса и состояние восстановления. |
| Доступ к панели | Сохранённые URL, логин и первоначальный пароль, доступные root. Изменение пароля через CLI/веб-панель не обновляет его копию в состоянии автоматически. |
| Резервная копия БД | Потоковый `pg_dump -Fc` и закрытые копии Compose, env и состояния. Самостоятельная копия выполняется онлайн; перед копией для обновления API останавливается. |
| Сменить API-токен | Скрытый ввод готового токена управления, проверка доступа к `/api/nodes`, атомарное сохранение. Токен подписок не меняется. Старый токен не отзывается: отзыв выполняется отдельно в панели. |
| Запустить панель | Запускает PostgreSQL, Valkey и backend, ждёт готовности. Подписка запускается отдельно. |
| CLI контейнера | Открывает официальный интерактивный `cli`, временно освобождая TUI; после выхода возвращает интерфейс. |
| Подписка → Установка / запуск | Использует сохранённые домен и настройки прокси. Запускает backend, проверяет токены, запускает подписку и ждёт Docker HEALTHCHECK. Восстанавливает предыдущую конфигурацию при обнаруженном незавершённом обновлении подписки. |
| Подписка → Обновление | Загружает сохранённый исходный тег образа, фиксирует digest и запускает его. При ошибке возвращает предыдущую конфигурацию и образ. |
| Подписка → Кастомизация | Официальный образ, свой совместимый образ или инструкция по Subpage Builder. Сторонний образ получает ограниченный токен подписок после подтверждения. Требуются порт 3010, совместимый API и собственный Docker HEALTHCHECK. |
| Подписка → Остановить | Останавливает только подписку. |

Обновление, остановка, резервная копия, смена токена и вход в CLI требуют подтверждения внутри приложения. Esc прерывает дальнейшее выполнение; завершённые действия сохраняются. Во время долгой операции интерфейс и системные метрики продолжают работать. Поздний результат отменённой операции не открывает её экран повторно. Между процессами действует общий lock.

Готовность подписки проверяется через встроенный HEALTHCHECK: запрос `/` без кода подписки у официального образа намеренно может завершаться разрывом соединения. Установка отдельно проверяет публичный TLS с доверием к системным CA и именем домена. Реальная страница пользователя находится по `https://домен/<shortUuid>`.

## Резервные копии и восстановление

Каталог копии: `/var/lib/remnamanager/backup-ДАТА-СЛУЧАЙНЫЙ_СУФФИКС`, права 0700. Успешная копия содержит `database.dump`, `compose.json`, `.env`, `subscription.env`, `panel.json` и маркер `COMPLETE`; права файлов — 0600. При прерывании файл остаётся с расширением `.partial` и не считается готовой копией. Дамп не проходит через память TUI и не попадает в журнал. Удаление старых копий автоматически не выполняется.

Перед запуском новой версии backend сохраняется `RecoveryBackup`. Если обновление завершилось ошибкой, прежний Compose восстанавливается, новый backend останавливается; старая версия автоматически не запускается поверх потенциально обновлённой схемы БД. Статус, логи, доступ и копия БД остаются доступны; остальные изменения заблокированы до проверки состояния.

При необходимости восстановления остановите backend и подписку. Используйте полный каталог с `COMPLETE`, сохраните текущее состояние для диагностики, восстановите Compose/env, затем запустите только БД и кеш. Для восстановления существующей БД используется `pg_restore --clean --if-exists --no-owner --exit-on-error -U postgres -d postgres` внутри `remnawave-db`, с подачей `database.dump` через stdin (`docker compose exec -T`). Эта операция заменяет данные содержимым копии: записи после момента копирования будут потеряны. После успешного восстановления верните соответствующий `panel.json` из того же каталога копии, затем запустите панель и подписку. Не очищайте `RecoveryBackup` до проверки совместимости схемы и образа. Для сохранения уже обновлённой БД потребуется выбрать совместимую версию backend и согласовать с ней Compose и `BackendTag` вручную.

Обновление подписки сохраняет предыдущий Compose и поле `SubRecovery` до подтверждения готовности. После аварийного завершения выберите «Страница подписки → Установка / запуск»: будет восстановлен прежний Compose, запущены сервисы и очищена запись восстановления после успешной проверки.

## Проверки и ограничения

Выполнены unit-тесты мастера, отмены, сохранения секретов, отдельных токенов, фильтрации и порядка постановки таймера отката. В Docker запущены настоящие backend/PostgreSQL/Valkey/страница подписок; проверены регистрация, повторный запуск API-bootstrap и ограничение прав токена подписок. Через Nginx и Caddy проверены HTTPS панели и реальная ссылка подписки с доверенными тестовыми CA. В отдельном сетевом namespace проверены синтаксис nftables, сохранение нужных TCP-портов, блокировка INPUT и DNAT/FORWARD, откат только собственной таблицы и сохранение сторонней NAT-таблицы.

Opt-in проверки находятся в `internal/installer/integration_test.go`. Обычный `go test ./...` не изменяет систему. Интеграционные тесты требуют отдельного тестового стека и переменных `RM_PANEL_FIXTURE`, `RM_PANEL_API`, `RM_NGINX_ENDPOINT`, `RM_CADDY_ENDPOINT`; не направляйте их на рабочую панель. `TestWriteLiveStackFixture` создаёт новые секреты: запускайте его только для нового пустого стека.

Публичная выдача ACME-сертификатов, systemd-таймер на настоящем VPS и восстановление после перезагрузки пока не проверены сквозным тестом. Docker-тесты с локальными CA не заменяют эту проверку.

Управление дополнительно проверяется `TestLiveComponentManagement` на одноразовом проекте `rmgo-management-test-*` при заданной `RM_MANAGEMENT_PROJECT`. Проверены настоящий `pg_dump` с чтением через `pg_restore --list`, статус/логи, запуск/остановка, фиксация digest подписки, смена сохранённого токена и полный цикл обновления backend. В этом тесте используется один и тот же известный образ backend с тестовой сменой метаданных версии, поэтому он проверяет порядок операций, а не реальные миграции между разными версиями. Поведение при сбоях миграции и необходимость ручного восстановления покрыты unit-тестами; автоматическое восстановление БД не заявляется.

Использованные спецификации: [Compose backend 3.4.9](https://github.com/remnawave/backend/blob/3.4.9/docker-compose-prod.yml), [переменные backend](https://github.com/remnawave/backend/blob/3.4.9/.env.sample), [Nginx](https://docs.rw/install/reverse-proxies/nginx/), [Caddy](https://docs.rw/install/reverse-proxies/caddy/), [Docker и firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/).
