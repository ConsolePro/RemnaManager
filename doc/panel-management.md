# Установка и управление панелью

Новые установки используют `/opt/remnawave/docker-compose.yml`, отдельные
`subscription/docker-compose.yml` и `subscription/.env`, а также каталоги
`nginx/` или `caddy/`. Существующие установки с `compose.json` и системным
прокси сохраняют прежний формат. Для явного перехода на Docker предназначена
операция «Сменить обратный прокси»; обновление менеджера само её не запускает.

Начиная с LayoutVersion 2 файлы создаются из готовых YAML-шаблонов
`internal/installer/templates/`. Для панели сохранены официальный Compose и
`.env.sample`; для прокси и подписки — примеры документации. Используются
`remnawave-network`, `remnawave-subscription-page`, `remnawave-nginx` и `caddy`.
При изменении образа правится только строка `image:`. Повторная настройка защиты
не заменяет пользовательские настройки Compose и `.env`. Существующий формат
LayoutVersion 0/1 автоматически не преобразуется, чтобы не сменить тома БД.

## Мастер

На экране выбора прокси клавиша **S** переключает размещение подписки: один
сервер или отдельный сервер через SSH. Прокси удалённого сервера выбирается
отдельно. Для Nginx клавиша **A** переключает Let's Encrypt и ZeroSSL.

SSH использует ключ из указанного файла либо ssh-agent. Пользователь должен
быть root или иметь sudo без пароля. Перед установкой показывается fingerprint
Ed25519; его нужно сверить с консолью сервера. Проверка host key обязательна.
Установка Docker и пакетов на обоих серверах входит в подтверждение мастера.
Второй экземпляр панели, PostgreSQL или Valkey на сервере подписки не создаётся.

Проверка DNS подтверждает разрешение имён, но не доказывает соответствие origin
или доступность внешних портов. Это явно отмечается в журнале этапов. Для CDN и
NAT окончательная проверка проходит через публичный HTTPS. Новая установка
Nginx использует TLS-ALPN-01: публичный TCP 443 временно передаётся через socat
на локальный 8443. Открыть только 8443 недостаточно. CDN, завершающий TLS, должен
быть отключён для такой проверки. Во время выпуска/продления принадлежащий этой
установке прокси кратко останавливается и затем запускается. Старые установки
LayoutVersion 1 сохраняют прежний HTTP-01.

## Управление

При входе в «Панель и компоненты» проверяются Compose, контейнеры, health-состояние,
API, прокси и соединение с удалённой подпиской. Сохранённая готовность установки
не считается доказательством текущей работоспособности. Частичная установка
доступна для продолжения мастера без генерации новых секретов и удаления базы.

Обычные start/stop/restart используют существующие контейнеры. Удалённая
подписка управляется своими командами SSH. Её образ обновляется на удалённом
сервере с сохранением прежнего манифеста. После оборвавшегося обновления
«Установка / запуск» восстанавливает предыдущий манифест. SSH-команды изменения
не повторяются автоматически при обрыве соединения.

Удалённая подписка обращается по HTTPS к ограниченному набору GET API панели:
subscriptions, subscription-page-configs и system/stats. Прокси допускает эти
запросы только с точным scoped Bearer-токеном подписки; права токена дополнительно
проверяет backend. Она не получает Cookie/TinyAuth/MFA-секреты панели. Прямой
доступ к административным API не открывается этим правилом.

## Сертификаты и смена прокси

Для LayoutVersion 2 Nginx использует один SAN-сертификат: при совместном
размещении в выпуск входят домены панели и подписки; TinyAuth добавляет домен
авторизации. При раздельном размещении сертификаты серверов независимы.
Рабочие файлы: `/opt/remnawave/nginx/fullchain.pem` и `privkey.key`.
acme.sh устанавливается в приватный каталог состояния менеджера; отдельно
проверяются регистрация аккаунта, результат выпуска, `--install-cert` и cron.
После регистрации проверяется сохранённый ACCOUNT_URL. При ошибке ZeroSSL
выбирается Let's Encrypt, проверяется повторная регистрация; только затем
запускается один `--issue` со всеми доменами. Если оба аккаунта недоступны,
выпуск и запуск зависимых компонентов прекращаются.
Повторный пропуск выпуска acme.sh (код 2) не вызывает принудительный перевыпуск.
Renewal hook проверяет Nginx и перезагружает работающий прокси; после перехода
на Caddy обновлённые PEM применяются через принудительный reload Caddy.

Caddy сохраняет `/data` и `/config` в своих постоянных каталогах. Для старых установок при переключении
его существующие PEM переносятся с проверкой домена, срока и соответствия ключа.
Для LayoutVersion 0/1, если сертификат нельзя безопасно найти или прочитать, операция останавливается
до выключения старого прокси. Скрытого нового выпуска при миграции нет.
Импортированные сертификаты обслуживает ежедневный systemd timer
`remnamanager-certificates.timer`: переход на acme.sh происходит при сроке
менее 30 дней. Caddy получает HTTP-01 webroot для этих сертификатов.

В LayoutVersion 2 при смене Caddy на Nginx может потребоваться новый общий
SAN-сертификат вместо отдельных сертификатов Caddy. Это указано в подтверждении
операции. При обратном переходе общий сертификат переиспользуется; его продление
сохраняет ACME pre/post hooks и применяет обновлённые PEM в работающем прокси.

Новые Compose используют документированные bind-mount файлов конфигурации;
поэтому менеджер редактирует эти файлы с сохранением inode. Nginx использует Docker DNS resolver для
application upstream, чтобы пересоздание backend/подписки не оставляло старый IP.

Перед переключением создаётся копия, проверяется конфигурация, записывается
журнал восстановления. При ошибке возвращается старый прокси и проверяется его
защита. После аварийного завершения повторная операция сначала восстанавливает
старый прокси. Абсолютное отсутствие простоя не обещается. Смена защиты Docker-
установки также резервируется и восстанавливает старую конфигурацию при ошибке.

Старые Certbot lineage и конфигурация системной установки не удаляются. После
явной миграции такой установки необходимо проверить её прежние Certbot renewal
задания: автоматическое отключение чужих или общих lineage не выполняется.

## Состояние и резервные копии

Состояние остаётся в существующем `/var/lib/remnamanager/panel.json`.
Секретные поля сохраняются как AES-256-GCM ciphertext; ключ `state.key` хранится
отдельно с правами 0600. Старый private JSON читается и переводится в новый
формат при следующем сохранении. Утрата ключа или подмена ciphertext приводит
к ошибке, а не генерации новых паролей. Ключ защищает от раскрытия одного JSON;
доступ root к полному каталогу позволяет прочитать секреты. Это не замена
шифрованию диска или отдельно зашифрованному внешнему архиву.

Каждая новая копия содержит PostgreSQL custom dump, конфигурации, состояние
с собственным ключом, метаданные образов и SHA-256 manifest. Docker-данные прокси,
включая сертификаты, входят в снимок. Для MFA сохраняются users с TOTP. Для
TinyAuth снимается архив SQLite-volume с краткой остановкой сервиса и последующим
запуском, если он работал до копирования. Копия не получает COMPLETE при ошибке.
Читать или переносить нужно весь каталог копии, включая его `state.key`.

Восстановление проверяет целостность, совпадение доменов, защиты, прокси и формата
каталогов, создаёт pre-restore копию, останавливает приложение и восстанавливает
БД вместе с соответствующей версией Compose. Обратные миграции Prisma не запускаются.
Сбой оставляет запись RecoveryBackup; запуск прежней версии на новой схеме БД
автоматически не выполняется. При восстановлении данные после даты снимка будут
заменены. Это восстановление той же управляемой установки, а не импорт чужого
сервера или автоматическая миграция между версиями PostgreSQL.

Удаление панели требует DELETE и итогового подтверждения. DELETE ALL дополнительно
удаляет её резервные копии. Удалённая подписка не удаляется вместе с панелью:
её SSH-параметры сохраняются, доступен отдельный пункт удаления. После удаления
основной панели API для оставленной подписки будет недоступен. Сохранённые копии
доступны из меню и после удаления панели.

## Диагностика WASM

В меню есть «Диагностика прокси и WASM». Можно передать точный путь `/assets/…wasm`
из Network браузера. Отчёт содержит два запроса, HTTP-версию, Content-Type,
Content-Encoding, Cache-Control, ETag, Vary, размер, время получения заголовков и
полное время. Второй запрос отправляет If-None-Match, если ETag был выдан.
Дополнительно читаются логи и активная конфигурация Docker Caddy через его
внутренний admin endpoint. Значения секретов маскируются в отчёте и журнале команд.
При TinyAuth/MFA без браузерной сессии ответ авторизации не является WASM-ресурсом.

Добавлены zstd/gzip в Caddy и gzip/WASM MIME в Nginx. Заголовки кеширования
приложения не заменяются выдуманным immutable для всех ресурсов.
Причина задержки редактора 30–60 секунд на пользовательском сервере **не установлена**.
Для завершения этой проверки нужен реальный URL, браузерная сессия и повторные
открытия редактора при выключенном Disable cache. Следует сравнить HAR Nginx/Caddy,
проверить повторную загрузку, компиляцию и инициализацию WASM по отдельности.

## Проверки и их границы

В этой среде проверены Go-тесты и vet, Linux-тесты установщика в контейнере,
сборки Linux amd64/arm64, синтаксис shell и изолированные реальные Nginx 1.30/
Caddy 2 с Cookie, TinyAuth и MFA. API-допуск удалённой подписки проверяется
отдельной матрицей. Данные и TOTP MFA проверяются после перезапуска gateway.

Для повторения Docker-проверок:

```powershell
./tests/panel-protection.ps1 -Go ./path/to/go.exe
./tests/panel-protection.ps1 -Go ./path/to/go.exe -Remote
./tests/panel-protection.ps1 -Go ./path/to/go.exe -Official
./tests/panel-protection.ps1 -Go ./path/to/go.exe -Official -Remote
```

Тестовые проекты используют собственные имена, порты localhost, синтетические
учётные данные и удаляются после проверки. Это не проверка установки на
публичном VPS: реальный ACME-выпуск, firewall, SSH/sudo отдельного сервера,
реальные shortUuid и браузерный сценарий требуют стенда с доменами и доступом.
