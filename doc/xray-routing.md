# Клиентские схемы Xray

«Маршрутизация Xray → Создать схему» объединяет раздельную маршрутизацию,
балансировку подключений, клиентский WireGuard/WARP и VLESS-цепочки в одном
шаблоне подписки **XRAY_JSON**. Требуется Remnawave с поддержкой `injectHosts`
(по официальной документации — 2.6.3 или новее) и клиент, использующий Xray JSON.
Обычная VLESS-ссылка не содержит эти правила.

## Как создать схему

1. Выберите исходный XRAY_JSON в панели. Менеджер создаёт отдельный шаблон;
   Default и исходный шаблон сохраняются.
2. Пробелом выберите подключения для группы `main`, нажмите Enter.
3. При необходимости добавьте группы, дополнительные выходы и правила.
   Стартовая схема направляет `.ru`, `.su`, `.рф`, `geosite:category-ru`
   и `geoip:ru` напрямую, остальной TCP/UDP — через `main`.
4. Выберите выход по умолчанию, откройте предварительный просмотр и подтвердите.
5. В панели назначьте созданный XRAY_JSON хосту-получателю либо подходящему
   правилу/группе подписки. Обновите подписку в клиенте.

Для `injectHosts` хост-получатель должен быть включён и видим, а выбранные
подключения — включены и доступны пользователю через его сквады. Менеджер
выбирает подключения по UUID из видимых и скрытых (`selectFrom: ALL`).
Скрытие, клонирование хостов, создание пользователей и изменение сквадов
автоматически не выполняются.

Для стартовой схемы клиенту нужны базы GeoIP/GeoSite с категориями `ru`
и `category-ru`. Наличие баз на сервере ноды не обеспечивает их наличие
на устройстве пользователя. Если клиент не поставляет их, настройте обновление
баз в клиенте или измените правила.

## Группы и правила

В каждой группе можно выбрать до 64 подключений. `leastPing` вместе с
`observatory` проверяет доступность и выбирает подключение с меньшей задержкой.
Проверка по умолчанию обращается к `https://www.gstatic.com/generate_204`
каждые 30 секунд. Если группа недоступна, её резервный выход — блокировка;
автоматического перехода на прямое соединение нет.

Выход правила: `direct`, `block`, группа подключений либо импортированный выход.
Порядок правил меняется Ctrl+↑/↓, удаление — Del. Доменные условия разделяются
`;` (это сохраняет запятые внутри регулярных выражений), IP/CIDR и протоколы —
запятыми. Домены и IP в одном правиле трактуются как альтернативы; другие
условия, например сеть и порт, применяются к обеим альтернативам.

Правила схемы идут первыми, затем сохраняются ограниченные условиями правила
исходного шаблона. Исходные правила, содержащие только выход и сеть,
заменяются новым общим маршрутом. Остальные настройки исходного шаблона,
включая DNS, сохраняются. Существующий неявный `proxy` в сохранённых правилах
заменяется выбранным выходом по умолчанию. Теги `rm-` зарезервированы менеджером.
Исходный шаблон с уже настроенным `injectHosts` или `burstObservatory`
для создания новых групп не поддерживается: мастер откажет до изменения панели.

## Клиентский WARP / WireGuard

Добавьте выход и укажите абсолютный путь к готовому WireGuard-профилю на сервере
менеджера, например `/root/wgcf-profile.conf`. Файл должен содержать один Interface
и один Peer: PrivateKey, Address, PublicKey, Endpoint и AllowedIPs. MTU
необязателен, по умолчанию 1280; поддерживается дополнительный `Reserved` из
трёх байтов. AllowedIPs сохраняются, а не расширяются до всего Интернета.

Импорт не выполняет команды PostUp/PostDown, не меняет DNS системы, не создаёт
аккаунт Cloudflare и не устанавливает сетевой интерфейс на ноде. Он создаёт
WireGuard-outbound **на устройстве пользователя**. Для выхода через Cloudflare
нужен действующий профиль WARP; произвольный WireGuard-профиль не становится WARP.
PreSharedKey и несколько Peer не поддерживаются.

Ключ профиля попадает в подписки всех получателей этого шаблона. Не используйте
в таком шаблоне учётные данные, которые нельзя передавать его получателям.
Это отличается от серверного WARP Native в примере eGames, где интерфейс
WireGuard работает на сервере ноды. Перенос серверного WARP Native в Go-менеджер
этим клиентским мастером не выполняется.

## VLESS-мост

Укажите файл с VLESS-ссылкой **отдельного транзитного пользователя** и входную
группу ровно с одним подключением. Поддерживаются RAW/TCP, WS, gRPC, XHTTP,
TLS и Reality с обычными параметрами и `encryption=none`.

Клиент строит цепочку: устройство → выбранная входная нода → VLESS-выход.
Соединение с выходом использует `sockopt.dialerProxy` входного подключения.
Это клиентская цепочка, а не автоматическая установка серверного моста.
Служебного пользователя и его доступы создайте в панели самостоятельно.
Его VLESS-учётные данные также будут доступны получателям шаблона.

## Сбои и удаление

Предварительный просмотр сохраняет журнал без записи в API панели. После
подтверждения менеджер создаёт новый шаблон и проверяет сохранённый JSON.
Журналы и секреты хранятся в `/var/lib/remnamanager/routing`, каталог 0700,
файлы 0600. Секреты не показываются на экране списка и результатов.

При потере ответа API выберите «Схемы и незавершённые операции → Продолжить /
проверить». Уникальное имя позволяет найти уже созданный шаблон без дубликата.
Если ответ создания потерян, найденная неназначенная заготовка принимается
как исходный снимок для её настройки; до завершения операции не редактируйте
эту заготовку в панели. Изменение сохранённого шаблона вручную блокирует его
автоматическую перезапись и удаление. Изменение исходного шаблона или выбранных
подключений между просмотром и применением требует нового просмотра.

Удаление касается только неизменённого шаблона этой схемы. Менеджер проверяет
его назначения в хостах, внешних сквадах и настройках подписки. Используемый
шаблон сначала нужно отвязать в панели. Настройки нод и подключения сохраняются.

## Проверки и источники

Go-тесты проверяют граф маршрутов, приоритеты, префиксы инжекта, изоляцию
секретов, продолжение после потери ответов API, запрет перезаписи ручных
изменений, навигацию и отображение полей в небольшом терминале.
`tests/xray-template-fixture.py` скачивает официальный Xray v26.7.28 с проверкой
SHA256 и проверяет девять сформированных конфигураций командой `run -test`,
включая стартовую схему РФ с официальными GeoIP/GeoSite.
Вместо панели тест подставляет тестовые outbounds с теми же тегами. Проверка
не подтверждает доступы реальных пользователей, сетевое соединение WARP
или работоспособность конкретного клиентского приложения.
