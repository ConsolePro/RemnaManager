# Мастер установки панели

Вход: «Управление панелью → Панель и страница подписки».
Порядок вопросов: размещение → домены и SSH → Caddy/Nginx → SSL только
для Nginx → Cookie/TinyAuth/MFA → асинхронная предварительная проверка →
сводка и подтверждение → установка и проверка HTTPS → инструкции входа.
Esc сохраняет введённые параметры. Пароли и API-токены маскируются.

## Изменения и переиспользование

- `internal/ui/install_wizard.go`, `install.go`, `model.go`, `view.go`,
  `subscription_remote.go`, `manage.go`, `menu.go`: экраны и переходы на
  существующих компонентах Bubble Tea, проверка до подтверждения,
  операции изменения доменов (`L`) и сертификатов после установки.
- `internal/services/services.go`: параметры SSL и SSH-пароля, интерфейс
  предварительной проверки.
- `internal/installer/panel_preflight.go`, `panel_certificates.go`,
  `subscription_password.go`: проверка DNS API и пользовательских PEM,
  передача SSL в исполнение и SSH по паролю с обязательной проверкой ключа.
- `panel_artifacts.go`, `official_templates.go`, `real.go`, `state.go`:
  загрузка официальных артефактов backend 3.4.9 с SHA-256, их применение,
  сохранение версии источника. Используется прежний механизм Compose,
  проверки health/readiness и firewall с подтверждением SSH.
- `state_secrets.go`, `manage.go`: SSH-пароль и DNS-токен в существующем
  зашифрованном состоянии; маскирование секретов в диагностике.
- `official_acme.sh`, `panel_acme_cron.sh`, `subscription_remote.go/.sh`:
  DNS-01, зашифрованные токены продления, проверка cron при повторе установки.
- `panel_configuration.go`, `backups.go`: изменения без миграции размещения,
  резервная копия с контролем целостности, журнал восстановления,
  откат прокси, окружения и настроек продления при ошибке.
- `protection.go`: существующие Cookie, TinyAuth и MFA сохранены;
  финальные инструкции содержат соответствующие адреса и начальные пароли.

## Один или два сервера

На одном сервере панель и подписка используют существующие официальные
Compose, общую сеть и выбранный прокси. Nginx использует общий SAN-сертификат
для панели, подписки и, при необходимости, TinyAuth.

На втором сервере устанавливаются только подписка, Docker и выбранный
прокси; база и панель остаются на первом. Подписка обращается к панели по
HTTPS с отдельным токеном через существующие ограниченные публичные маршруты.
SSH-пароль передаётся через Go SSH, без argv, файлов пароля и истории shell.
Ключ сервера подтверждается пользователем до проверки подключения.

## SSL и защита

Caddy получает и продлевает HTTPS автоматически. Nginx предлагает acme.sh,
Cloudflare, Gcore, Bunny.net и импорт PEM. Существующий acme.sh использует
TLS-ALPN-01 на публичном 443 с локальным 8443; HTTP-01 не заявляется.
Один сервер получает один SAN-сертификат и одно продление; два сервера —
независимые сертификаты и задания продления.

DNS-01 использует проверенные хуки `dns_cf`, `dns_gcore`, `dns_bunny`.
Проверяется чтение зоны через API; права записи окончательно подтверждает
успешный DNS-01. Точные SAN-имена сохраняются вместе с wildcard под каждым
выбранным именем (например, `example.co.uk` и `*.example.co.uk`), без
угадывания границ зоны. Покрытие apex и вложенных доменов не предполагается
автоматически.
Постоянные A/AAAA-записи мастер не создаёт.

Токен для cron зашифрован OpenSSL; ключ находится в отдельном закрытом файле.
Сохранение токена DNS-хуком в открытый account/domain config отключено.
Импорт PEM проверяет пару ключ/сертификат, срок и имена; успешность публичной
цепочки дополнительно проверяется при HTTPS-проверке. Пользовательский PEM
не объявляется автоматически продлеваемым; прежнее ACME-продление снимается.

Cookie использует прежнюю секретную ссылку и защищённую cookie с отказом 403.
TinyAuth сохраняет существующую интеграцию и отдельный домен `auth.<панель>`;
после выбора защиты мастер предлагает подтвердить этот домен. MFA сохраняет
существующий портал `/r`, обязательную регистрацию второго фактора и механизм
восстановления. Внутренние порты остаются привязанными к loopback.

## Проверки и границы

Добавлены матрицы 36 комбинаций для TUI и реального рендеринга Compose,
прокси и команд исполнения; проверки шифрования, подмены официальных
артефактов, DNS API, PEM и локальный SSH-сервер для пароля, изменённого ключа
и отмены. Linux-тесты исполняют DNS-01/cron с моками, включая отказ ACME,
шифрование токенов и сохранение посторонних cron-заданий.

Это локальные и изолированные проверки. Реальные DNS-провайдеры, выпуск
публичных сертификатов, два внешних сервера и интерактивная регистрация MFA
требуют отдельной проверки на тестовой инфраструктуре. Изменение доменов
и сертификатов поддерживается для официального Compose-формата; старые
форматы требуют отдельной явной миграции. Автоматической миграции между
одним и двумя серверами нет.
