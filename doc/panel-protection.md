# Защита панели в Go-версии

Запуск меню менеджера: `sudo re` или `sudo remanager`. Команду `remna` Go-установщик больше не занимает. Во время обновления старый бинарный файл менеджера переносится в `/usr/local/lib/remnamanager/remna.previous`, только если метаданные Go подтверждают его принадлежность RemnaManager. Существующая сторонняя команда `remna` сохраняется.

Все три режима доступны при выборе любого фронтового прокси:

| Защита | Nginx | Caddy | Дополнительный домен |
| --- | --- | --- | --- |
| Cookie (по умолчанию) | Да | Да | Не нужен |
| Страница входа TinyAuth | Да | Да | `auth.panel.example.com` |
| Портал входа с MFA | Да | Да | Не нужен; портал в `/r` |

## Cookie-защита (по умолчанию)

Мастер создаёт независимые случайные имя и значение cookie по 256 бит. Ссылка имеет вид:

```text
https://panel.example.com/auth/login?rm_<случайное-имя>=<случайное-значение>
```

Открытие правильной ссылки устанавливает cookie с `Secure`, `HttpOnly`, `SameSite=Strict`, путём `/` и сроком семь дней. Прокси сразу перенаправляет на `/auth/login` без секретного параметра. После этого отображается штатная форма входа Remnawave: cookie не заменяет пароль панели.

Без правильного cookie или при неверном ключе ссылка возвращает HTTP 403. Проверка охватывает все маршруты панели, включая API, OAuth-пути и WebSocket handshake. Обхода по заголовку `Authorization` нет. Работа менеджера через локальный API и внутреннее соединение страницы подписки с backend сохраняются.

Правильный секретный параметр принимается только на `/auth/login`. Ключ и значение хранятся в `/var/lib/remnamanager/panel.json` (0600), не меняются при продолжении установки. Просмотр ссылки: «Панель и компоненты → Доступ к панели». После удаления cookie, его истечения или смены браузера откройте секретную ссылку снова.

Журнал доступа Nginx для панели выключен; Caddy не включает access log. Ответ со ссылкой содержит `Cache-Control: no-store` и `Referrer-Policy: no-referrer`. Конфигурация Nginx с ключом имеет права 0600, Caddy — 0640 и группу `caddy`. Ссылку следует хранить как пароль: тот, кто её знает, может пройти этот дополнительный слой защиты.

## Отдельный вход TinyAuth

Выберите TinyAuth в мастере. Укажите дополнительный домен, являющийся прямым поддоменом панели:

```text
Панель:    panel.example.com
TinyAuth:  auth.panel.example.com
Подписки:  sub.example.com
```

Для всех трёх доменов нужны A/AAAA на сервер; HTTPS для TinyAuth настраивает выбранный прокси. Такой домен позволяет TinyAuth установить cookie для `panel.example.com`, не распространяя сессию на соседний публичный домен подписок.

Для TinyAuth создаётся отдельный случайный пароль. Имя пользователя совпадает с именем администратора, но пароль отличается от пароля панели. Оба набора данных доступны в «Доступ к панели». Последовательность: вход в TinyAuth → штатный вход Remnawave.

Используется официальный образ `ghcr.io/tinyauthapp/tinyauth:v5.2.0`, без Docker socket и сторонних расширений. Контейнер слушает только `127.0.0.1:3020`; публичный доступ проходит через HTTPS-прокси. Nginx проверяет сессию через `auth_request`, Caddy — через `forward_auth`. При остановке TinyAuth доступ к панели закрывается. Публичные API-клиенты без его сессии или учётных данных также не проходят.

Пароль хешируется bcrypt внутри Go. Контейнер получает хеш через закрытый `tinyauth.env`, а исходный пароль остаётся в закрытом состоянии менеджера для повторного просмотра. Данные сессий хранятся в Compose-томе `tinyauth-data`. Резервная копия менеджера включает конфигурацию и хеш; активные SQLite-сессии TinyAuth в неё не входят, после восстановления может потребоваться повторный вход.

## Портал входа с MFA

Третий вариант — отдельный портал AuthCrunch/Caddy Security, как в Caddy-конфигурации eGames. Он развёртывается локальным шлюзом за выбранным Nginx или Caddy, а не заменяет выбранный фронтовый прокси. Шлюз доступен только на `127.0.0.1:3030`, HTTPS обслуживает фронтовый прокси.

Вход: `https://panel.example.com/r`. Скрипт создаёт администратора с отдельным случайным начальным паролем. При первом входе нужно зарегистрировать второй фактор — приложение TOTP или аппаратный ключ. Один пароль не открывает панель. После успешного входа в портал остаётся штатная авторизация Remnawave. Управление факторами: `/r/settings/mfa`; создание ключей для программных клиентов: `/r/settings/apikeys`.

Учётные записи, факторы и ключи хранятся в томе `mfa-data`, пароль начальной настройки и ключ подписи — в закрытом состоянии менеджера. Перезапуск и переключение на другой режим не удаляют том. Значение начального пароля не обновляется автоматически, если его изменили в портале. При повторном развёртывании с прежним томом начальный пароль не перезаписывает существующую учётную запись.

На amd64 используется закреплённый digest официального `remnawave/caddy-with-auth` с Caddy 2.9.1 и модулем авторизации 1.1.27. Этот образ не содержит arm64: на arm64 установщик собирает локальный образ из тех же закреплённых версий. Для сборки нужен исходящий доступ к Docker Hub и Go proxy, свободное место и память для Go-компиляции. Обычный Caddy на хосте не требует дополнительных модулей.

## Внешний API: два независимых допуска

`Authorization: Bearer <токен панели>` сохраняется и передаётся backend без подмены. Дополнительный слой защиты также обязателен:

| Режим | Дополнительный допуск |
| --- | --- |
| Cookie | `Cookie: ИМЯ=ЗНАЧЕНИЕ` из секретной ссылки |
| TinyAuth | `X-Api-Key: Basic base64(логин:пароль TinyAuth)` либо браузерная сессия |
| MFA | `X-Api-Key: <ключ из /r/settings/apikeys>` либо полноценная MFA-сессия |

Для TinyAuth только подзапрос проверки получает Basic из `X-Api-Key`; исходный Bearer остаётся для Remnawave. После проверки `X-Api-Key` удаляется перед отправкой в backend. То же разделение действует в MFA-шлюзе. Запрос с правильным дополнительным ключом, но неверным Bearer, отклоняет уже API панели.

```sh
# Cookie
curl -b 'ИМЯ=ЗНАЧЕНИЕ' -H 'Authorization: Bearer <токен панели>' https://panel.example.com/api/nodes
# TinyAuth; значение после Basic — base64 от логина и пароля TinyAuth
curl -H 'X-Api-Key: Basic <base64>' -H 'Authorization: Bearer <токен панели>' https://panel.example.com/api/nodes
# MFA
curl -H 'X-Api-Key: <ключ портала>' -H 'Authorization: Bearer <токен панели>' https://panel.example.com/api/nodes
```

API не выводится из-под защиты отдельным публичным маршрутом. Дополнительных исключений для OAuth-путей также нет. Локальный API менеджера и внутренний API для страницы подписки работают напрямую внутри сервера/Compose.

Резервная копия в режиме MFA включает `mfa.env`, `mfa.Caddyfile` и `mfa-users.json` с пользователями, факторами и API-ключами. Невалидная или неполная копия не получает маркер `COMPLETE`. При восстановлении остановите MFA-шлюз, восстановите его конфигурацию и состояние из той же копии, затем перенесите `mfa-users.json` в `/data/users.json` тома `mfa-data` с правами 0600 перед запуском сервиса. Для записи в том можно использовать одноразовый `docker compose run --rm -T --no-deps --entrypoint sh mfa-gateway -c 'umask 077; cat > /data/users.json' < /путь/к/копии/mfa-users.json`. Активные сессии портала в копию не входят; после восстановления войдите заново.

## Уже установленная панель

Для старой Go-установки выберите «Панель и компоненты → Защита панели», затем Cookie, TinyAuth или MFA. Для TinyAuth сначала подготовьте DNS дополнительного домена. Операция запускает сервисы панели, не меняет пароль Remnawave и данные PostgreSQL. Возможна краткая недоступность HTTPS при перенастройке Nginx и выпуске сертификатов.

Обновление бинарного файла менеджера само по себе не меняет прокси работающей панели. Старая установка без ключей помечается предупреждением в данных доступа. После успешной настройки менеджер проверяет, что анонимный запрос блокируется, а разрешённый доступ работает.

Если операция прервана, сохраняется `ProtectionPending`. Выберите тот же режим и домен в «Защита панели», чтобы продолжить с уже созданными секретами. До завершения другие изменения компонентов блокируются; статус, логи, данные доступа и резервная копия доступны. При смене TinyAuth или MFA на другой режим прежний сервис останавливается, его том сохраняется.

Общедоступная страница подписки на отдельном домене не получает эту дополнительную защиту. Управление ранее установленной Bash-панелью и автоматический импорт её состояния не входят в эту операцию.

## Проверки

`go test ./...` проверяет секреты, сохранение при повторе, запрет открытой конфигурации без ключей, восстановление после сбоя настройки, состав резервной копии MFA и экраны мастера. Отдельный Docker-тест `tests/panel-protection.ps1` проверяет настоящие Nginx/Caddy, TinyAuth и MFA с локальным тестовым CA и синтетическим backend. Проверяются все шесть сочетаний, неверные ключи и cookie, блокировка API и OAuth-путей, очистка URL, настоящий вход TinyAuth, обязательность второго фактора, регистрация TOTP, неверный/правильный код, выдача ключа портала и выход из сессии. Проверяются внешний API с двумя независимыми ключами и сохранение TOTP после перезапуска шлюза. Это не проверка выдачи публичных сертификатов ACME на VPS.

Схема изучена по [eGamesAPI/remnawave-reverse-proxy](https://github.com/eGamesAPI/remnawave-reverse-proxy/) и [описанию внешнего API](https://wiki.egam.es/ru/configuration/external-api/). Интеграция использует [TinyAuth/Nginx](https://tinyauth.app/docs/guides/swag/), [TinyAuth/Caddy](https://tinyauth.app/docs/community/caddy/), [настройки TinyAuth](https://tinyauth.app/docs/reference/configuration/) и [официальный пример MFA Remnawave](https://github.com/remnawave/caddy-with-auth/tree/main/examples/minimal-security-setup-with-mfa).
